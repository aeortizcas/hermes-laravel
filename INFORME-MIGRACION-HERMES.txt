--------------------------------------------------------------------------------
1. OBJETIVO
--------------------------------------------------------------------------------
Migrar la tienda en línea del monolito PHP legacy a un stack moderno:
Laravel 12 (backend) + Inertia.js + React (frontend), reutilizando el esquema
MySQL existente (49 tablas, dump db_drcr-3_6_jul_2025.sql) para no perder
compatibilidad con los datos de producción.

Alcance de la FASE 1 (acordado con el usuario): flujo comercial público de
punta a punta:
  - Portada / catálogo con búsqueda
  - Filtrado por categoría de producto
  - Ficha de producto con galería de imágenes
  - Carrito (sesión) con cantidades
  - Checkout que guarda el pedido en las tablas legacy (tbl_master/tbl_detalle)

Fuera de fase 1 (próximas fases): autenticación/login, pago (PayPal),
administración de productos, seguimiento de envíos, facturación y reportes,
migración de esos mismos módulos en el admin.

--------------------------------------------------------------------------------
2. QUÉ ES EL SISTEMA LEGACY (resumen del análisis)
--------------------------------------------------------------------------------
- Nombre interno: Hermes (repo "hermesfull"), BD "db_drcr".
- ~423 archivos PHP (~44.5k líneas), 49 tablas MySQL, PHP procedural sin
  framework, mezcla mysqli/PDO, HTML/PHP con CSS/JS inline, jQuery/Bootstrap/
  DataTables/FPDF copiados a mano, fragmentos de Vue 2.
- Módulos principales: storefront (index2.php, show1.php, insert.php…),
  carrito/pedidos basado en tablas (tbl_master/tbl_detalle/tbl_venta),
  seguimiento de envíos (seguimiento_envio*.php, tbl_rastreo, tbl_tracking*),
  facturación (factura/, reports/ con FPDF), CRUDs administrativos duplicados
  (país/departamento/ciudad/proveedores/unidades/peso/…), contenido (videos,
  slideshows, suscripciones), API para app Android (HeroApi/), app de
  escritorio Java Swing (DesktopApp/).
- Riesgos detectados (documentados, no corregidos en legacy): credenciales de
  BD de producción en texto plano (db.php, controller/db.php, HeroApi/db.php),
  claves SSH en la raíz (Uchihamadara001, *.pub, authorized_keys…), passwords
  hardcodeadas (factura/helloworld.php…), SQL por interpolación (queries.php),
  subidas de archivo sin validación fuerte. Importante: rotar credenciales si
  el repo llegara a ser público.
- Peculiaridades del esquema que condicionan la migración:
  * El PRECIO de un producto NO está en tbl_producto: vive en tbl_venta
    (filas CV='V' y cestado=1; se toma la más reciente como "precio vigente").
  * El STOCK se calcula con tbl_entrada (stipo 'E' entradas − 'S' salidas,
    nestado=1). Hay además tbl_unidades_restantes (vacía, no usada).
  * El carrito/pedido legacy = filas en tbl_master (cabecera: cestado=1,
    sbi=0) + tbl_detalle (líneas: cestado=1, Y=1).
  * register es la tabla de clientes/usuarios (name, email, password con
    mezcla de bcrypt y cifrado AES legacy).
  * Categorías de producto: tbl_categories (el producto referencia por
    tbl_producto.idec). La tabla `categories` era solo menú.

3. DECISIONES DE ARQUITECTURA (tomadas con el usuario)
--------------------------------------------------------------------------------
1) Alcance fase 1: "Storefront core" (catálogo → producto → carrito → checkout).
2) Arquitectura: Laravel + Inertia.js + React (una sola app, sin API separada).
3) Base de datos: "Reuse schema as-is" (mismos nombres de tablas/columnas).
4) Entorno: instalar PHP/Composer/MySQL para correr localmente.

CAMBIO DE ENTORNO (importante): este Mac es macOS 12.7.6 (Monterey, Intel).
Homebrew 6.x ya no publica bottles para macOS 12 → compilar php@8.3/aspell/etc.
desde fuente requería 1-2 h y los procesos de brew morían en modo no interactivo.
MySQL tampoco publica binarios para macOS 12 (404 en cdn.mysql.com).
SOLUCIÓN ADOPTADA (equivalente a la intención del usuario):
  - PHP 8.3.33 estático autónomo compilado con static-php-cli (spc).
  - Desarrollo local sobre SQLite que ES UN ESPEJO del esquema MySQL original
    (convertido con hermes-laravel/scripts/convert_dump.py desde el dump).
  - La app está lista para MySQL en producción: solo cambiar .env
    (DB_CONNECTION=mysql, DB_DATABASE=db_drcr, usuario/contraseña) y apuntar
    al dump original; los modelos/consultas son portables (Eloquent).
    SQLite de desarrollo: database/database.sqlite (49 tablas, integridad ok).
    SQLite de pruebas:  database/testing.sqlite (copia para phpunit).

6. MAPEO ESQUEMA LEGACY → MODELOS / CÓDIGO
--------------------------------------------------------------------------------
  Tabla legacy          Modelo Eloquent (App\Models)
  --------------------  ----------------------------------------------
  tbl_producto          Product
  tbl_producto_imagenes ProductImage (portada/cEstado, url => /uploads/products)
  tbl_categories        ProductCategory (el producto enlaza por idec)
  tbl_venta             Sale (precio; active = CV='V' y cestado=1)
  tbl_entrada           InventoryEntry (stipo E/S, nestado)
  tbl_master            OrderMaster (cestado=1 + sbi=0 => abierto)
  tbl_detalle           OrderDetail (cestado=1 + Y=1 => línea activa)
  register              User (clientes)
  images                Slide (slideshow de portada)
  tbl_main_menu         MainMenu   (no usado aún en UI)
  tbl_submenu           Submenu    (no usado aún en UI)

Reglas replicadas (con consultas limpias; el legacy usaba joins que
multiplicaban filas y daban números erróneos):
  - Precio vigente = fila más reciente de tbl_venta con CV='V', cestado=1
    por producto (subconsulta ORDER BY idventa DESC LIMIT 1).
  - Stock/unidades restantes = SUM(ncantidad) stipo='E' − SUM(ncantidad)
    stipo='S' (nestado=1). Si <= 0 => producto AGOTADO.
  - Solo se muestran productos con precio vigente Y con imagen de portada
    (equivalente a los INNER JOIN del legacy).
  - IVA 15 %: carrito/checkout muestran subtotal, IVA y total; el total
    coincide con el cálculo legacy (subtotal * 1.15).

Desviaciones deliberadas (documentadas):
  - El carrito ahora vive en la SESIÓN del navegador (antes: filas sueltas en
    tbl_master/tbl_detalle por cada click). Es más limpio y permite guest.
  - Al confirmar el pedido (checkout) se persiste 1 cabecera (tbl_master:
    dfecha=Hoy, idusuario=cliente, cestado=1, sbi=0) + 1 línea por producto
    (tbl_detalle: cestado=1, Y=1) + 1 fila histórica de precio (tbl_venta con
    cestado=0, para NO alterar el precio de catálogo que usa cestado=1).
  - El cliente se busca/crea en register por email (los passwords legacy son
    una mezcla de bcrypt y AES: la autenticación completa llega en fase 2).
  - Sin pago real en fase 1: el pedido queda "pendiente" y la pantalla de
    confirmación lo indica; PayPal/transferencia = fase 2.

8. CÓMO EJECUTARLO
--------------------------------------------------------------------------------
Requisitos normales (máquina con PHP >= 8.2, Composer, Node >= 20):
  cd hermestotal-main/hermes-laravel
  composer install
  npm install
  cp .env.example .env && php artisan key:generate   (si no existe .env)
  # Base de datos:
  #   - Local dev sin MySQL: ya está database/database.sqlite (espejo del dump).
  #     Para regenerarlo desde el dump original:
  #       python3 scripts/convert_dump.py ../hermestotal-main/db_drcr-3_6_jul_2025.sql database/database.sqlite
  #   - Producción/MySQL real: editar .env (DB_CONNECTION=mysql, DB_HOST,
  #     DB_PORT, DB_DATABASE=db_drcr, DB_USERNAME, DB_PASSWORD) e importar el
  #     dump original en MySQL.
  npm run build        # compila el frontend (o "npm run dev" para desarrollo)
  php artisan serve    # servidor en http://127.0.0.1:8000

En ESTA máquina (PHP estático, sin MySQL):
  export PATH=/tmp/spc/buildroot/bin:$PATH
  cd hermestotal-main/hermes-laravel
  php artisan serve
  npm run build   (ya compilado)

Pruebas:
  php vendor/bin/phpunit
  # copia la BD de dev a testing si hace falta:
  cp database/database.sqlite database/testing.sqlite
